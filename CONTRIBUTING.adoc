= Contributing to Hibernate Migration Recipes
:toc:

== Project organization

This project provides migration recipes across the Hibernate family of projects. It currently builds one recipe JAR, with Hibernate ORM as the first supported project. All production recipes remain in Gradle's standard `main` SourceSet. Separate test SourceSets keep the original application's dependencies separate from the dependencies used to execute converted code.

[cols="2,3",options="header"]
|===
|Location |Purpose
|`src/main/java` |Production recipes and shared recipe helpers.
|`src/main/resources/META-INF/rewrite` |Declarative YAML recipes packaged in the recipe JAR.
|`src/test/java` |Unit tests for version-independent test infrastructure, such as `FixtureBundleUnitTest`.
|`src/migrationSources<Migration>/java` |Valid migration inputs compiled against the source ORM/JPA API, separate from recipes and test code.
|`src/conversionTest<Migration>/java` |Conversion tests, validation helpers, and fixture generators for a migration path. Currently: `conversionTestOrm80`.
|`src/conversionIntegrationTest<Migration>/java` |Tests that execute generated fixtures against the target project runtime. Currently: `conversionIntegrationTestOrm80`.
|`src/testSupport/java` and `src/testSupport/resources` |Shared test helper sources and fixture catalogs compiled or copied into each test suite that uses them.
|`buildSrc/src/main/kotlin` |The local Gradle plugin that creates migration test SourceSets, configurations, and tasks.
|`buildSrc/src/test/kotlin` |Unit tests for that Gradle plugin.
|===

In the paths above, <Migration> is a naming placeholder, such as Orm80, not a literal directory name. The conversion SourceSets also support their ordinary `resources` directories. `testSupport` is a shared source directory, not a separate SourceSet or published library. Its Java sources are compiled separately into `test`, `conversionTestOrm80`, and `conversionIntegrationTestOrm80`.

Only `main.output` belongs in the production JAR. Keep validation utilities, fixture generators, and runtime test code in the test directories.

=== Recipe organization

Recipes live in `src/main/java` under appropriate `org.hibernate.migration.recipes` sub-packages.

`org.hibernate.migration.recipes.table` defines OpenRewrite datatable / diagnostic support.

See link:README.adoc#_available-migrations[Available Migrations] for details about currently available migrations.

== Conversion testing model

=== Conversion correctness

Conversion tests use the source project dependencies alongside OpenRewrite and the production recipes. The current example is the `conversionTestOrm80` suite. Tests check the transformation itself, including expected edits, unchanged unsupported inputs, comments, and skipped-migration diagnostics.

The existing ORM suite demonstrates this model through the `org.hibernate.migration.testing.ApiValidation` helper in that SourceSet, which performs the full compilation-based check for fixtures using it:

. Compile the original Java against the selected source API environment.
. Parse that Java with OpenRewrite using the same environment.
. Run the recipe and collect its actual output.
. Compile the emitted Java against the target API environment.
. Reparse against the target API and run the recipe again to check idempotence.

The `validateChangedJavaSourcesAfterRecipe` callback used by the concise `RewriteTest` examples sees only changed Java files. It does nothing for unchanged-only tests and cannot include unchanged supporting files. Use `ApiValidation.run` with complete inputs when compilation of unchanged fixtures or cross-file dependencies is part of the contract. Deliberately invalid or attribution-deficient fixtures use explicit raw-parser tests.

Selecting the SourceSet does not automatically attach this helper to every test. Wire new applicable conversion tests into it explicitly. Deliberately invalid input tests and XML tests need their own appropriate assertions.

=== Compiled migration inputs

The `migrationSourcesOrm80` SourceSet provides ordinary Java files with IDE support
and compilation against the configured source ORM/JPA environment. Its only declared
dependency is the source Hibernate Core API, using `compileOnly`; JPA comes from that
dependency graph. It does not inherit recipe or JUnit dependencies. Conversion tests
and fixture generation depend on its compilation and track its Java sources as task
inputs. Its compiled classes are not added to either test suite or the generator's
runtime classpath, and are not packaged in the production JAR.

Source-compatible Java inputs use this SourceSet, including QueryFlushMode,
named-query, delegate, map-key, composite, and temporal scenarios. Independent
scenarios use distinct packages so all inputs compile together. Finite syntax
matrices use checked-in Java variants instead of assembling Java in the tests.
Use normal source formatting, including tabs and expanded method bodies. Omit
Javadoc from migration inputs unless it is part of the behavior being tested.
The runtime inputs are `fixture/Migrated.java`, `fixture/TemporalEntity.java`,
and the Java files under `xmlfixture/`.
`MigrationSources.configured()` reads from the source root supplied by Gradle through
`migration.sources`. Use `files(...)` for selected files or `scenario(...)` for all
Java files under a scenario directory. Both preserve source-root-relative paths.
Conversion tests and generators consume these original file contents, not the
compiled input classes.

Keep target compilation and fresh-target idempotence validation with `ApiValidation`.
Compilation of this SourceSet validates the source ORM/JPA environment.
Deliberately invalid or attribution-deficient inputs stay outside the compiled
SourceSet. Inputs that require target-only APIs also stay outside this source
SourceSet. Expected-output text and small assertions about preserved source
regions may remain inline; XML-specific tests continue to construct their XML
inputs. Preserve line endings when adding fixtures for CRLF behavior, and assert
diagnostics against the actual fixture paths and original file coordinates.

Recipe-specific conversion suites own API validation and diagnostic cases. `TemporalDiagnosticsTest` checks reporting precedence and original coordinates; temporal runtime verification separates value contracts from persistence and isolates reflection in a fixture-access helper.

This suite also checks recipe discovery from the built JAR and exclusion of test classes from that artifact. Target compilation uses an explicit target classpath; do not replace the source parser classpath with the target API simply to make output compile.

=== Runtime behavior

Compilation cannot establish whether converted code behaves correctly with a target Hibernate project. Integration tests execute actual recipe output against that project’s runtime and the services needed for the scenario.

The current `conversionIntegrationTestOrm80` suite uses ORM 8 and a database to test named mutation statements, map-key mappings, and delegate access. Other projects may need different services and runtime assertions.

Keep the target runtime classpath separate from source-version and production recipe dependencies. Shared test support must avoid assuming that OpenRewrite or source-version classes are available. In the ORM suite, the target classpath contains ORM 8, test dependencies, and the database driver.

Keep syntax variations and unchanged-input checks in the conversion suite. Add runtime coverage when a transformation changes behavior that compilation cannot establish.

== Current build convention: Hibernate ORM

The testing model above applies across projects, but the current convention implements ORM environments specifically. It resolves Hibernate Core, verifies ORM/JPA dependency identities, and requires a database dependency. Adding another Hibernate project requires extending this build support; a different migration name alone does not provide that support.

The root `build.gradle.kts` applies `org.hibernate.migration-testing`, implemented by `MigrationTestingPlugin` in `buildSrc`. Its `migrationTesting` block declares:

* `environments`: reusable named ORM releases.
* `migrations`: source and target environment names, a database dependency, and optionally a fixture-generator main class.

The current environment and migration declarations are:

[source,kotlin]
----
migrationTesting {
    environments {
        register("orm74") {
            ormVersion.set("7.4.11.Final")
        }
        register("orm80") {
            ormVersion.set("8.0.0.Beta2")
        }
    }
    migrations {
        register("orm80") {
            sourceEnvironment.set("orm74")
            targetEnvironment.set("orm80")
            databaseDependency.set("com.h2database:h2:2.4.240")
        }
    }
}
----

The current path is `orm74` (ORM 7.4.11.Final, JPA 3.2.0) to `orm80` (ORM 8.0.0.Beta2, JPA 4.0.0-M7). JPA versions come from the published ORM dependencies. Conversion tests use the source ORM environment, which includes its published JPA API.

XML validation uses schemas from the target ORM JAR under `org/hibernate/jpa/` and `org/hibernate/xsd/mapping/`. Published ORM artifacts come from Maven Central; no local ORM build or publication is required.

For a migration named `orm80`, the convention creates `migrationSourcesOrm80`, `conversionTestOrm80` and `conversionIntegrationTestOrm80`, their standard Gradle dependency configurations, and `generateConvertedFixturesOrm80`. Each environment also has isolated compile and runtime dependency configurations.

`verifyMigrationEnvironments` checks the selected ORM and JPA versions against the declared environments and the suite classpaths. It writes helper metadata to `build/migration-testing/environments.properties`. This is generated output, not a configuration file to edit.

To add another ORM migration with the current convention, declare its environments and migration path, then add the corresponding conversion tests, integration tests, and fixture generation support. Reuse an existing environment when it becomes the source of a later upgrade. Keep production recipes in `main`; do not create a production SourceSet or JAR for each version. Source and target validation both use the JDK running Gradle.

The generator main class currently defaults to the ORM 8 fixture generator. A future migration must provide an appropriate generator rather than accidentally reusing that default. Convention registration alone does not create fixtures or tests.

== Adding another Hibernate project

Keep new production recipes and YAML definitions in `main` so they ship in the same recipe JAR. Choose names that identify the project and migration scope, and add the available path and its limitations to the README.

Extend the build convention to describe the new project’s dependency coordinates, source and target environments, version checks, and required runtime services. Retain separation between source-based conversion testing and target runtime testing. Do not impose ORM, JPA, or database requirements on projects that do not need them.

Provide the migration’s test directories, fixture catalog, generator, and integration assertions. Reuse shared fixture and reporting support where appropriate; the existing ORM-specific `ApiValidation` helper and generator may need adaptation. Add build-convention tests for any new registration or dependency behavior. Substantial extensions follow the design process described below.

== Generated fixture handoff

Integration tests consume generated recipe output through a validated fixture handoff. The following paths and classes describe the currently implemented ORM example.

The current fixture catalog is `src/testSupport/resources/orm80-fixtures.properties`.
`fixture/Migrated.java` in the compiled migration-input SourceSet supplies the shared
runtime Java input. The temporal runtime input and XML runtime Java inputs also
come from this SourceSet; `XmlRuntimeFixtures` supplies the XML descriptor inputs.
`ConvertedFixtureGenerator` applies the recipes for every
declared variant. XML fixtures include emitted descriptors alongside Java sources
in the same hashed manifest; runtime checks consume those actual emitted files.
`XmlRecipeSupport` validates XML against the published schemas and checks idempotence.

`generateConvertedFixturesOrm80` writes the results under `build/converted-fixtures/orm80/<variant>/<fixture>/sources` and publishes a manifest after successful generation. `FixtureBundle` manages and validates that handoff, including source hashes, expected files, and dependency identities. Missing, extra, corrupt, or stale outputs fail validation.

The integration task depends on generation. Generation runs independently of JUnit selection, so filtering conversion tests cannot publish an incomplete fixture set. Do not hand-write the transformed Java consumed by integration tests or edit generated files under `build`.

When adding an integration scenario, update the original fixture, catalog where needed, generator dispatch, and runtime assertions together. Catalog entries must be understood by the generator; adding a properties entry alone is insufficient.

== Running checks

Use the Gradle wrapper with a JDK supported by Gradle and the project dependencies. Compilation, fixture generation, and tests use the JDK running Gradle; the build does not select or download a separate toolchain. CI currently uses JDK 25. Production Java compilation uses a Java 17 release target; test and fixture compilation use the build JDK's version.

[source,shell]
----
# Full project verification, including the build convention's tests
./gradlew check

# One ORM recipe's conversion tests
./gradlew conversionTestOrm80 --tests '*MigrateMapKeyNameToValueTest'

# Generate ORM 8 integration fixtures without executing runtime tests
./gradlew generateConvertedFixturesOrm80

# ORM 8 runtime checks; generates fixtures automatically
./gradlew conversionIntegrationTestOrm80

# Shared infrastructure unit tests only
./gradlew test

# Build convention unit tests only
./gradlew -p buildSrc test
----

`test` alone is not full recipe verification. `check` includes the registered conversion suites, environment verification, ordinary unit tests, and `verifyBuildConvention`. The last task runs the separate `buildSrc` test build.

Pinned tooling: Gradle 9.8.0, Rewrite BOM 3.37.0 (Rewrite 8.89.0), JUnit 6.1.3. The current ORM integration suite uses H2 2.5.252.

Dependency versions are explicit or BOM-aligned. The builds do not use dependency locking. Keep project-specific environment checks when changing dependencies; the current checks verify ORM/JPA identities.

== XML schema context maintenance

`mapping-comment-contexts.properties` records the paths to the seven comment-bearing types in the published `mapping-7.0.xsd`. Each entry maps a parent schema type and child element name to its schema type. The same paths also identify many-to-many mappings for removal of ignored orphan-removal attributes. The Hibernate mapping recipe follows this graph from the document root and stops at foreign namespaces or unknown contexts. This keeps aliases such as `inverse-join-column` eligible without matching arbitrary similarly named elements.

`MappingXmlCommentsTest` derives reachable uses from the published source schema and tests their conversion. It also validates representative output against `mapping-8.0.xsd`, including the differing comment positions for collection tables, secondary tables, and table generators. When extending schema support, update this context table and ordering rules together with those checks.

Each XML schema family has one recipe and one descriptor visitor. `MigratePersistenceXml` includes package-descriptor conversion, `MigrateOrmXml` updates JPA mapping metadata, and `MigrateMappingXml` includes comment conversion and removal of ignored many-to-many orphan removal. `DescriptorVisitor` checks root metadata once, visits content, and applies the version/schema update only when no content candidate was skipped. It discards all proposed edits for a conflicted document while retaining original-source diagnostics. `XmlDocumentMigrationTest` verifies complete migration in a single visitor invocation and isolation between documents.


== Build-file coordinate verification

The ORM coordinate suite generates Gradle (both DSLs, including local TOML catalogs),
Maven, Ivy, and Maven Ant Tasks builds from actual recipe outputs before resolver
checks. Source and target versions come from the migration environments. Maven
3.9.11, Ivy 2.5.3, Maven Ant Tasks 2.1.3, and Ant 1.10.18 are isolated test tools;
they are not production recipe dependencies. Maven Ant Tasks uses an HTTPS mirror
and a dedicated local repository. Resolver caches are separate from generated files.
The Gradle checks use the project's running Gradle distribution.

Production resource processing substitutes the aggregate coordinate target from
`orm80`'s configured target environment. A resource regression test changes that
configuration and verifies incremental regeneration without ORM resolution.
